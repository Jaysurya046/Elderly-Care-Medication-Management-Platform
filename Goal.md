Project: Elder Care & Medication Management Platform
0. Your role and working method

You are a senior full-stack engineer and healthcare-product engineer. Build a production-quality MVP of a platform that helps older adults manage medicines, doctor appointments and daily care routines, while keeping family and caregivers informed through consent-based access.

Working method

Work in the phases in section 12. After each phase: run lint, type-check, tests and build, fix failures, write a short summary, and commit.
Ask questions only when a decision is blocking and cannot be reasonably defaulted. Otherwise make a sensible assumption and record it in docs/DECISIONS.md with a one-line rationale.
Do not invent medical facts, dosages or drug interactions. Use only data the user enters or imports.

1. Non-negotiable principles
The elder is in control. The elder owns the profile, approves every access grant, can revoke any grant instantly, and can mark items as private. No caregiver action may bypass consent.
Every sensitive action is audited. Reads of health data, writes, grant changes, exports and deletions each produce an AuditLog entry. Audit logs are append-only.
Minimum necessary data. Store only what the features need. Never return password or passcode hashes in any API response.
No medical advice from software. The system must never recommend, change or create a dosage or schedule automatically. AI or OCR output is always a draft that a human confirms. Show a visible "Not medical advice" notice wherever AI text appears.
Emails are safe by default. Reminder emails do not name medicines or diagnoses unless the elder explicitly enables this per profile. The default says "You have medicines due at 8:00 AM. Open the app to see them."
Accessibility is a requirement, not polish. Target WCAG 2.2 AA throughout, with elder-specific settings described in section 7.
Time is always local to the elder. Store all instants in UTC. Compute schedules, reminders and "today" using the profile's IANA timezone. Default to Asia/Kolkata for new profiles, configurable per profile. Handle DST transitions correctly.

1. Access model (decided)

Accounts. Owners and caregivers have an email-and-password account. An account can be a member of several care profiles.

Care profile. Each profile has an owner (the elder, or a delegated owner if the elder cannot manage their own account). Profile ownership can be transferred, but never without the elder's confirmation.

Roles and scopes. A membership links one account to one profile with a role and explicit scope flags:

Roles: OWNER, CAREGIVER (can manage medicines and appointments), FAMILY (view-only, plus alerts), EMERGENCY_VIEWER (emergency card only).
Scopes, each on or off: view_medications, manage_medications, view_appointments, manage_appointments, view_notes, write_notes, receive_missed_dose_alerts, view_private_items.
Defaults: FAMILY receives missed-dose alerts but not private items. CAREGIVER gets the medicine and appointment scopes but not private items unless the elder grants them.

Invitations. The elder or an OWNER creates an invitation. It contains a single-use, random token (stored hashed) that expires after 7 days. The invitee must accept while signed in with the invited email address. The elder confirms the role and scopes before the membership becomes active.

Passcodes (two distinct uses).

Member passcode (4–6 digits): used for quick unlock of a profile on a shared device, for example a tablet in the elder's kitchen. It is hashed, rate-limited (5 failures per 15 minutes per membership, then a cooldown), and cannot be used on its own to access a profile. It always requires an active account session.
Emergency code: a separate 8-character code that the elder can print. It opens only the emergency card, with no edit rights. It can be rotated at any time.

Revocation. Every request checks membership and scopes against the database. Revoking a membership or changing its scopes takes effect on the next request. This is non-negotiable.

Authorisation helper. Implement a single function, requireProfileAccess(profileId, { role?, scope }), used by every route and server action. It throws a typed error, and the error is logged to the audit trail. Add a test that fails if any route touches health data without calling it.

6. Core behaviour
6.1 Dose lifecycle

Use a single state machine, implemented in packages/core and tested exhaustively:

PENDING becomes TAKEN when the dose is taken on time, and LATE_TAKEN when taken after MISSED.
PENDING becomes SNOOZED, which pushes the due time forward by snoozeMinutes. A dose can be snoozed at most three times.
PENDING becomes SKIPPED only with a reason.
PENDING becomes MISSED automatically when scheduledAt + graceMinutes has passed with no action.
MISSED can become LATE_TAKEN or SKIPPED.
TAKEN, LATE_TAKEN and SKIPPED are final except through a logged correction by an OWNER or CAREGIVER.

Stock rules. Decrement stockCount exactly once per dose, at the point it becomes TAKEN or LATE_TAKEN. Use a conditional database update so two simultaneous actions cannot double-decrement. Stock never goes below zero.

Concurrency. Two people acting on the same dose at once: the first valid transition wins, and the second receives a "already recorded by X" response.

6.2 Dose generation
Generate DoseEvent rows for the next 14 days, extended daily by the worker.
Generation is idempotent because of the unique key on (scheduleId, scheduledAt).
Schedule edits affect future events only. Past events are never rewritten.
6.3 Reminders and escalation

All reminder jobs are idempotent: the job ID and NotificationLog.referenceKey are derived from the event and the recipient, so retries cannot send duplicates.

Event Rule
Upcoming dose Send 15 minutes before scheduledAt, to the elder only
Dose due now Send at scheduledAt, only if still PENDING
Missed dose Mark MISSED at scheduledAt + graceMinutes. Send to the elder if email is enabled
Escalation If a CRITICAL dose is still MISSED after a further 60 minutes, send to members with receive_missed_dose_alerts who also have escalateToCaregivers enabled
Appointment Send at startsAt - offset for each offset. For travel-aware reminders, use startsAt - travelMinutes - 60 as the leave-by alert
Low stock When stockCount <= refillThreshold, notify OWNER and CAREGIVER once per 48 hours

Digest grouping. Doses due at the same local time are sent as one email, not one per medicine.

Quiet hours. Default 22:00 to 06:30 in the profile timezone. Non-critical reminders are deferred to the end of quiet hours. Critical doses ignore quiet hours.

Email content. Subject and body follow section 1, principle 5. Every email includes a link to the app and a one-line unsubscribe or preference link where the law requires one.

6.4 Adherence and insights
Adherence = (TAKEN + LATE_TAKEN) / (scheduled doses that are not in the future and not SKIPPED with a valid reason). Show the calculation on hover or on a details page.
Streak = consecutive days with no MISSED doses.
Insights are descriptive only. For example: "Evening doses were missed 4 times this week." Never prescriptive ("change the dose"). Insights are generated by deterministic rules in packages/core, not AI, in this phase.
6.5 Appointments
Sorted by startsAt in the profile timezone.
The appointment prep view is a deterministic template in this phase: current medicines, recent missed doses, open care notes, and a blank list for the elder's own questions. Add a "questions to ask the doctor" field the elder can fill in.
6.6 Emergency card
A print-optimised page at /profiles/[id]/emergency with @media print styles, a large-font layout, and the name, date of birth, blood type, allergies, conditions, current medicines, primary doctor, emergency contacts and hospital.
Accessible through a signed-in member with view_medications, or by anyone with the emergency code.
Viewing it is logged in the audit trail.
7. Accessibility and Senior Mode

Two modes.

Senior Mode (/senior): one clear "Today" timeline. Morning, Afternoon, Evening and Bedtime blocks. The next dose is shown first with large buttons: "I took this", "Remind me in 15 minutes" and "Skip (tell us why)". Settings are limited to text size, contrast and read-aloud.
Care Circle Mode (/dashboard): full management, adherence charts, the activity feed and the audit view.

Requirements

Base body text 18px minimum in Senior Mode, with a text-size setting up to 28px. All layouts must work at 200% zoom.
Touch targets at least 48×48px, with at least 8px spacing between them.
Contrast at least 4.5:1 for text, and 7:1 in high-contrast mode.
Never rely on colour alone. Every status has an icon and a text label.
Every action is reachable by keyboard, with a visible focus ring.
Form inputs have visible labels, not just placeholders. Errors are announced via aria-live, and each error explains how to fix it in plain language.
Destructive actions (deleting a medicine, revoking access, deleting a profile) need a confirmation dialog that states the consequence in plain words.
Plain-language copy: short sentences, no medical jargon in the elder's view, and a reading level no higher than roughly grade 6 for Senior Mode.
Read-aloud: a button that reads the current dose name, strength and instructions using the Web Speech API. Degrade gracefully if the API is unavailable.
Reduced motion respected. No auto-playing audio.
Language: all UI strings go through an i18n layer, English is complete, and the structure is ready for Hindi and Marathi.
8. Security, privacy and compliance
Argon2id for passwords and passcodes. Never log them, and never return them.
Rate limiting on login, passcode, invitation acceptance and password reset. Use Redis-backed limits, not in-memory limits, so they work across instances.
Encrypt TOTP secrets and any stored OCR text at rest with an application key from the environment. Store the key in a secrets manager in production.
TLS only in production. HSTS, CSP and the other standard security headers on every response.
CSRF protection on all state-changing requests.
Data export: a JSON bundle of everything the elder owns, delivered through a time-limited signed link. Exports are audited.
Account and profile deletion: a 30-day grace period, after which data is hard-deleted except for audit records that the law requires us to keep. Document the retention period in docs/THREAT_MODEL.md.
Write a short privacy notice and consent screen at onboarding. Record the consent version in the database.
Write a data processing summary aligned with GDPR principles and relevant Indian rules (DPDP Act 2023). Do not claim certification. State that a qualified legal review is needed before production use with real patient data.
AI features are off by default and require explicit enablement by the elder.
